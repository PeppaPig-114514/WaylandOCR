# PrtScOCR OCR 引擎 / 参数「精度-延迟」基准测试报告

- 测试对象：`rapidocr 3.9.2`（ONNXRuntime CPU EP），PP-OCRv6 tiny/small/medium、PP-OCRv5 mobile
- 测试机：Intel i5-12490F（6 物理核 / 12 线程），无 GPU
- 测试脚本：`bench/bench.py`（合成测试集 + 全量评测）、`bench/summarize.py`（出表）、`bench/analyze_errors.py`（错误分类）
- 原始数据：`bench/results.json`（第一轮）、`bench/results_quiet.json`（第二轮）、`bench/results_mix.json`（混合 det/rec 补充实验）
- 结论：**出厂默认配置（`limit_type=min`, `limit_side_len=736`）在这个场景下慢了约 25 倍**；「随手框选一块屏幕区域 + 中英混排 + 硬性 <300ms」应改用 **`PP-OCRv6 tiny` + `limit_type=max` + `limit_side_len=960`**（小区域中位 72ms，微平均字符错误率 0.0056）；如果能接受 ~400ms 或愿意用混合模型，可拿到约 2.7 倍的字符准确度提升（字符错误数 8 → 3）。

> **数据可信度声明**：测试期间本机并非空闲（详见 §1.2），延迟数字是**上界**，约含 10%~20% 的外部负载膨胀；所有配置在同一轮评测中**逐图交错执行**，因此配置之间的对比是公平的，但「某个配置到底是不是 300ms 以内」这类绝对值判断请连同 §1.2 的负载说明一起看。所有 CER 数字为确定性结果，两轮完全一致。

## 1. 环境与测量条件

### 1.1 软硬件

- Python 3.12.14（`/home/peppapig/PrtScOCR/.venv/bin/python`）
- Linux 7.0.0-34-generic（glibc 2.43）
- CPU：Intel i5-12490F，6 物理核 / 12 逻辑线程
- `rapidocr 3.9.2`、`onnxruntime 1.30.0`、`opencv-python 5.0.0`、`numpy 2.5.3`、`Pillow 12.3.0`
- onnxruntime 可用 provider：`['AzureExecutionProvider', 'CPUExecutionProvider']` → 实际使用 CPU
- 未修改 `.venv` 中任何依赖版本；测试期间 rapidocr 自行下载了 **PP-OCRv6 medium** 权重（det 62.1MB + rec 76.6MB，来自 modelscope，下载成功，约 4 秒）；tiny/small/v5-mobile 权重为环境自带，全部校验通过
- 测试期间 onnxruntime 线程配置保持出厂（`intra_op_num_threads=-1`，即用满物理核）
- 送图方式：内存中的 BGR `ndarray`（不含磁盘 IO）；`use_cls=False`（按任务要求关闭方向分类）

### 1.2 外部负载（重要）

测试机同时运行着本项目自己的 OCR 常驻服务（`lib/ocrd.py --foreground`）和桌面环境。用 `/proc/<pid>/stat` 逐进程采样（5 秒间隔，共 198 个采样点）得到：

| 区间 | 整机忙碌 | 基准进程占用 | **其他进程占用（外部负载）** |
|---|---|---|---|
| 基准运行期间（125 个采样） | 中位 6.00 核（=物理核满载） | 中位 5.05 核 | **中位 0.89 核**，峰值 3.99 核 |
| 基准空闲期间（73 个采样） | 中位 1.08 核 | 0 | **中位 1.08 核**（常驻 daemon + GUI） |

即：外部负载约 **0.9~1.1 个物理核，占整机算力 ~15%~18%**，偶发突发更高。因此：

1. 表中延迟为**上界**，真实空闲机器上应更低（粗略量级 -10%~-20%，这是估计不是测量）；
2. 两轮完整评测中同一配置的中位延迟相对差异为 **1%~25%**（见 §4.6），**低于 ~20% 的延迟差异不应被视为显著**；
3. `load average` 在本机不可用（基准自身的 6 个推理线程会把 load 推到 20+），所以本报告改用「核数」口径描述负载。

### 3.1 对比配置

注意：`Det.model_type` / `Rec.model_type` / `ocr_version` 这些键在 `params` 里**必须传枚举**（`ModelType.TINY`），传字符串会抛 `TypeError: The value of Det.model_type must be Enum Type.`（这是实测踩到的坑，脚本里已按枚举传值）。

### 3.2 归一化规则与 CER

**主口径（`normalize_ws`）**，即报告里「宏平均 CER（主）」：

1. 删除零宽字符（U+200B/200C/200D/FEFF）；
2. 所有 Unicode 空白（含全角空格 U+3000、`\t`、`\xa0`）统一替换为半角空格；
3. 按行切分，每行去掉首尾空格，行内连续空格压成一个空格，丢弃空行；
4. 用 `\n` 重新拼接（多行结果按行拼接后比较；`\n` 也计入 GT 长度分母）。

不做大小写折叠，不做全角/半角标点互转。

**辅助口径 1（`normalize_ws_insensitive`）**：在主口径基础上**删除所有空白**再比较。理由是：文本重建器在 CJK 与拉丁/数字交界处是否补一个空格，取决于框的几何间隙，属于「重建器的选择」而非模型的识别能力；保留空格会把这类系统性偏差算成 OCR 错误。本报告用该口径做「真正的字符错误」判断。

**辅助口径 2（`normalize_nfkc`）**：主口径 + NFKC（把全角标点/数字折成半角），用于量化「全角/半角混淆」这一类错误。

CER = 字符级 Levenshtein 编辑距离 / GT 长度（脚本内自实现两行滚动 DP）。空 GT 时：hyp 也为空记 0，否则记 1。宏平均 = 12 张图 CER 的算术平均；微平均 = 12 张图编辑距离之和 / GT 字符之和。

### 3.3 阅读顺序重建

`result.boxes` + `result.txts` 需要自己拼回文本。脚本实现了两种顺序：

- `row`（默认，单栏）：按 y 中心分行（同一行判定阈值 `0.60 × 行高`），行内按 x 排序；同一行内相邻两段若水平间隙 `> 0.55 × 文本高度` 则补一个空格，否则直接拼接。
- `twocol`（两栏）：先按图片中线把框分到左右两栏，各自按行重建，再「左栏整体 → 右栏整体」拼接（与 09 号样本的 GT 顺序一致）。

**这是评测口径的一部分**：同一个模型，用行优先顺序读两栏图，CER 会从 0.011 变成 0.769（§4.7）。也就是说 rapidocr 本身不做版面分析，多栏阅读顺序必须由调用方处理。

### 3.4 计时方法

- 每个「配置 × 图片」：**预热 1 次**（结果丢弃）+ **计时 3 次**，取 3 次的**中位数**（`--timed-runs` 可调）。
- 计时范围：包含送图前的可选 2 倍放大与 `engine(img, use_cls=False)` 的完整调用（`time.perf_counter`）；不含磁盘 IO、不含图片加载。
- det/rec 拆分取自 `result.elapse_list`（rapidocr 源码中该值为 `perf_counter` 差值，**单位秒**，脚本已换算为 ms；`use_cls=False` 时中间元素为 `None`）。
- **逐图交错执行**：外层循环图片、内层循环配置，使时间上变化的外部负载对各配置影响均等（比「一个配置跑完再跑下一个」抗漂移）。
- 报告中的「中位延迟」= 各图 3 次计时中位数再取中位数；「P95 / 最大」= 把 12 张图的所有单次计时（36 次）汇总后取 95 分位 / 最大值 —— 注意该 P95 **包含 1920x1080 整屏图**，所以数字偏大；面向「随手框选」的决策请看 §4.5 的小区域子集。
- 两轮完整复测：第一轮 654s（load 口径见 §1.2），第二轮 696s；第二轮为 `bench/results_quiet.json`，本报告主表（表 1~4）用第二轮，§4.6 给出两轮对比。

### 3.5 「先放大 2 倍」消融

对 8 张 `font_px ≤ 15` 的小字样本，在送图前用 `cv2.resize(..., fx=2, fy=2, INTER_CUBIC)` 放大 2 倍，与不放大对比。因为 `limit_type=max` 只做「上限约束」、不会自动放大，所以：

- `B2x_max960`：720x112 → 1440x224 → 又被 max 压回 960 宽，实际只得到 1.33 倍有效分辨率；
- `B2x_max1920`：1440x224 不再被压缩，2 倍像素**真正**进入 det；
- 420x120 这类小图放大后 840x240 < 960，本身就得到完整 2 倍。

### 3.6 外部负载监控

测试期间另跑一个采样器，按 5 秒间隔从 `/proc/<pid>/stat` 累计所有进程的 utime+stime，扣除基准进程自身，得到 §1.2 的「其他进程占用核数」。

### 5.3 tiny 的精度差在哪里（可操作的结论）

tiny 不是「普遍更差」，它只在**三类可预测的场景**掉分（9 张小区域图上 4 处错误，全都在 07/10/11 号图）：

1. **ASCII 大小写与 O/0、C/c 混淆** —— `RapidOCR`→`RapidocR`、`OK:`→`0K:`、`Ctrl+Shift+O`→`Ctrl+Shift+0`。对代码、序列号、快捷键、订单号等「字母数字强区分」的内容是硬伤。
2. **全角标点** —— `！？`→`!?`、`（）`→`)`（还会丢掉半边的括号）。中文排版里的全角标点会被折成半角或丢失。
3. **代码/标点的细小间距** —— `def main():`→`def main() :`。

反过来，tiny 在**纯中文正文、中文+数字、低对比度灰字、两栏段落**上的表现与 small 没有可测量的差别（这些小区域图的「去空白 CER」全部为 0）；真正拉开差距的就是上面三类场景（深色终端 0.024 vs 0.008、设置对话框 0.017 vs 0.000、特殊符号 0.089 vs 0.044）。

## 6. 结论与推荐

### 6.1 针对「随手框选一块屏幕区域、中英混排、要求 <300ms」

**推荐默认配置（唯一能稳定达标）：**

```python
from rapidocr import RapidOCR, ModelType, OCRVersion

engine = RapidOCR(params={
    "Det.ocr_version": OCRVersion.PPOCRV6, "Det.model_type": ModelType.TINY,
    "Rec.ocr_version": OCRVersion.PPOCRV6, "Rec.model_type": ModelType.TINY,
    "Det.limit_type": "max",          # 关键：不要用 min
    "Det.limit_side_len": 960,        # 只用它做「上限」，不放大
    "Global.log_level": "error",
})
res = engine(img_ndarray, use_cls=False)
```

- 9 张小区域图：**中位 72ms（两轮取优）/ 87ms（单轮），P95 131~148ms，最慢单次 156ms** → 300ms 有 2 倍以上余量
- 12 张图微平均字符错误率 **0.0056（8/1419）**，宏平均 CER 0.040（主口径）/ 0.011（去空白）
- 相对出厂默认：**快约 24~27 倍**（两轮取优 1943ms / 72ms ≈ 27 倍；单轮 2091ms / 87ms ≈ 24 倍），字符错误 8 处 vs 3 处
- 代价（必须知情）：ASCII 大小写 / O-0 / 全角标点会出错（§5.3）。如果框选内容是代码、命令行、序列号、快捷键，建议改用下面的配置，或提供「重新识别（高精度）」按钮。
- **适用边界**：该延迟只对「小框选」成立 —— 框选宽度超过约 1000px 后 tiny 也会顶到 300ms：1200x230 实测 255~312ms，1920x1080 整屏为 701~1164ms。也就是说 300ms 保证大约覆盖「短边 <350px 且长边 <1000px」的区域；更大的区域要靠降低分辨率（如 max1280 的降采样）、限制最大边长或分块识别来兜底。

**若可接受 ~400~500ms（精度优先）：**

```python
params = {..., "Det.model_type": ModelType.SMALL, "Rec.model_type": ModelType.SMALL,
          "Det.limit_type": "max", "Det.limit_side_len": 960}
```

- 小区域 **中位 391ms（两轮取优）/ 510ms（单轮），P95 548~745ms** → **在本机不满足 300ms**，但字符错误降到 3/1419（微 CER 0.0021），深色终端与快捷键场景基本正确
- `limit_side_len=1280` 与 960 在精度上没有任何差别（12 张图逐图 CER 完全相同），延迟也在噪声内 → **用 960 即可，没有理由用 1280**

**性价比最高的折中（本次额外发现，建议 A/B 测试后作为备选）：**

```python
params = {..., "Det.model_type": ModelType.TINY, "Rec.model_type": ModelType.SMALL,
          "Det.limit_type": "max", "Det.limit_side_len": 960}
```

- 精度与 `small/small` **逐图完全相同**（3/1419，宏平均 0.032 vs 0.031）
- 小区域中位 **325ms**（单轮，未做第二轮），比 `small/small` 的 510ms 快 ~36%
- 仍略超 300ms，且本轮只有一次测量，**需要你自己复测确认**（`bench/bench.py --filter mix`）

**精度优先模式（不在乎延迟）：** `v6 medium + max960` 是本次字符错误最少的配置（1/1419，微 CER 0.0007），但小区域中位 **3737ms**、1920x1080 图 **33.9s**，比 small 慢 6~10 倍，而收益只有「3 处错误 → 1 处错误」。**不建议作为默认或常规「高精度模式」**；`small/small` 已经吃掉了绝大部分收益。

### 6.2 明确不推荐的项

| 项 | 原因（数据） |
|---|---|
| ❌ 出厂默认 `min/736` | 小区域 1943~2091ms（比 tiny 慢 ~24 倍），det 占 92% 耗时；精度并没有更好（3/1419，与 small/max 相同） |
| ❌ `limit_side_len=1280`（配 small 或 tiny） | 精度与 960 逐图完全相同，延迟无改善（甚至 tiny 在 1280 上更慢：91ms vs 72ms） |
| ❌ 送图前放大 2 倍 | 12px 样本 CER 完全不变（0.071 → 0.071），延迟几乎翻倍 |
| ❌ `v5 mobile max960` | 比 `v6 small max960` 慢（607ms vs 516ms）、字符错误更多（6 vs 3），1920x1080 上也不占优 |
| ❌ `small det + tiny rec` | 保留了 tiny 的全部识别错误（10 号图 0.160，全场最差），没有任何收益 |

### 6.3 为什么默认配置这么慢（机制说明）

`Det` 预处理有两条分支（`ch_ppocr_det/utils.py:resize`）：

- `limit_type="max"`：**只在 `max(h,w) > limit_side_len` 时按比例缩小**，小图保持原尺寸（再取整到 32 的倍数）。所以 420x120 的框选区域几乎原样送进检测网络。
- `limit_type="min"`：**只要 `min(h,w) < limit_side_len` 就放大**，使短边等于 `limit_side_len`。默认 736，于是 420x120 被放大 `736/120 ≈ 6.1 倍` → 约 2576x736；720x112 被放大 `736/112 ≈ 6.6 倍` → 约 4416x736。检测网络的算力消耗随像素面积增长，这就是 1.5~2.4 秒的来源（第二轮实测：A 在 420x120 上 1564ms、720x112 上 2389ms；合成图与真实截图区域的对比见 §7 局限 1）。

也就是说，**默认参数可以理解为是按「整页文档扫描」的假设调的（先放大短边保证小字可读），对「已经清晰、只是面积小的屏幕截图区域」是纯粹的性能浪费**；而实测表明这种放大并没有带来任何 CER 收益（§4.8 的 2 倍放大消融是同一结论的更强版本）。

## 7. 局限与不确定性（请连同结论一起看）

1. **合成图比真实截图「干净」**：PIL 灰度抗锯齿渲染，没有 ClearType/亚像素渲染、没有显示缩放、没有 JPEG 压缩、没有半透明叠加。真实截图上的绝对 CER 应当更高（尤其 12px 小字与低对比度场景），因此本报告的数字适合做**配置间比较**，不适合当成真实准确率承诺。
2. **样本量小**：12 张图 / 1419 个非空白字符；小区域子集只有 571 字符。「3 处 vs 8 处字符错误」是方向性结论，不是统计显著性结论（tiny 的错误是系统性的、可复现的，这点比数量更重要）。
3. **机器不空闲**：外部进程常年占用 ~0.9~1.1 个物理核（§1.2），延迟是上界；两轮复测显示同一配置的中位延迟可波动 1%~17%（medium 达到 25%~33%）。**低于 ~20% 的延迟差异不要当真。** 300ms 阈值附近的判定（B 的 391ms、H 的 325ms）受此影响最大；建议在空闲机器上复测这两个配置。
4. **归一化口径会显著影响 CER**：主口径（空白压缩）中 35~47 个编辑来自空格差异，远多于真实字符错误（0~6）。看精度请以「去空白」口径为准，看「端到端文本可用性」再看主口径。全角/半角标点被计为错误（我认为这对中文场景是必要的严格性），NFKC 口径的数字也在表中给出。
5. **文本重建是评测口径的一部分**：行分组阈值（0.6×行高）与补空格阈值（0.55×行高）是我选的经验值；换一组阈值会改变主口径 CER（但不会改变「去空白」口径的结论）。两栏样本必须用栏感知顺序，否则 CER 0.77（§4.7）。
6. **未测方向分类器**：按要求 `use_cls=False`。真实截图若可能倒置/旋转，需要打开 cls，会额外增加耗时（未测）。若打开，建议单独复测。
7. **未调 onnxruntime 线程数与 rec 批大小**：本轮使用出厂线程配置；`Rec.rec_batch_num=6`、`Rec.rec_img_shape=[3,48,320]` 均为默认。若要进一步压 rec 耗时（H 配置里 rec 占 87%），这些是下一步的调优点，但本报告没有数据。
8. **两栏的「栏感知顺序」需要调用方实现**：本报告的 `twocol` 顺序是按图片中线硬分栏的实现，只对等宽两栏有效；真实界面里的多栏/卡片布局需要更完整的版面分析。
9. **单位口径**：字号 = PIL 字体 em 像素，和浏览器 CSS px 的渲染尺寸接近但不完全等价；`elapse_list` 的 det/rec 拆分来自 rapidocr 内部计时，包含各自的前/后处理。
10. **未做 GPU / OpenVINO / MNN 等其他后端的对比**（环境没有可用 GPU 运行时），全部数据都是 onnxruntime CPU。
11. **「小区域」的定义**：本报告的小区域子集是「宽 ≤920 且高 ≤350」共 9 张（因此 1200x230 的两栏图与 1920x1080 整屏图不在内）。它们在表 3 里单列，延迟明显更高（tiny：两栏 255~312ms、整屏 701~1164ms），不要把它们当成「随手框选」的典型值。

## 8. 复现方式

```bash
cd /home/peppapig/PrtScOCR

# 1) 合成测试集 + 全量评测（约 11 分钟；到 bench/samples/ 看 12 张图）
#    会打印环境、测试集、9 张结果表（含 2 倍放大消融、错误样例）
.venv/bin/python bench/bench.py

# 2) 只跑某一类配置（子串匹配）或某些样本，并调整计时次数
.venv/bin/python bench/bench.py --filter mix --timed-runs 3      # 只跑混合 det/rec 配置
.venv/bin/python bench/bench.py --only-sids 01_crop,12_full --timed-runs 7

                                    --json2 bench/results.json

# 4) 错误分类统计（真实字符错误 / 空白差异 / 全角半角混淆）
.venv/bin/python bench/analyze_errors.py --json bench/results_quiet.json,bench/results_mix.json
```

**未改动项目其他文件**：`lib/` 下文件未做任何修改，`.venv` 中依赖版本未变（仅由 rapidocr 自行下载了 PP-OCRv6 medium 权重到 `site-packages/rapidocr/models/`）。
